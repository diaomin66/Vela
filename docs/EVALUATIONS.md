# 模型评测

ahaX 0.7.0 将「单次检测」与「定时评测」分成独立子页面，分别展示各自来源的记录。评测调用已保存渠道的 Responses API，使用全新上下文和明确题目，不读取编程任务或执行模型生成的系统工具。每次结果保留题目、原始回答、推理档位、耗时、服务商返回的 Token 用量和题库版本。

## 单次检测

1. 在渠道中启用需要测试的模型，然后打开「评测 → 单次检测 → 开始检测」。
2. 在「新建检测」中选择 1–6 个模型，同名模型在不同渠道分别测试。可以给每个模型选择不同的 API 推理档位；「API 默认」表示请求中不指定 effort，不代表原生模型目录的默认选择。
3. 选择糖果、鹈鹕动画和判题。可为糖果、判题指定评审模型，增加独立文字复评；同模型评审会明确标记。鹈鹕不追加自动评审。
4. 点击「开始检测」执行这一轮。鹈鹕显示动画画廊，糖果和判题按每次回答逐条排列；支持渠道筛选、重新播放动画、查看完整原文、历史比较及报告导出。可随时停止后续请求，网络错误不计作答错。

单次弹窗只负责执行本轮，不包含保存定时计划或启用定时的操作。该页面内的最近一次设置可继续使用；定时计划另行保存。切到「定时评测」不会取消正在执行的单次检测，两类任务共享一个运行名额，已有任务时不能再启动一轮。

一次被测回答计一次请求；启用复评后，每个有效的糖果或判题答案最多再发送一次评审请求。最多 6 模型 ×（3 道题 + 2 次复评）= 30 次请求，启动前显示当轮上限。没有自动重试。鹈鹕提供 32768 输出 tokens、128 KiB 回答空间，其他题目与评审保留 8192 tokens；响应超限、未完成或只有工具调用时明确报错。

「新建检测」和「定时计划」都提供「单次请求超时」。新计划默认 5 分钟，提供 2、5、10、30 分钟预设和 30–3600 秒自定义整数。每道题与独立评审分别拥有完整上限，包含等待响应头和接收响应体；连接建立上限仍为 15 秒。超时和网络中断分别提示，超时不计零分也不自动重试。运行开始时保存当轮设置，之后修改计划不影响正在执行的请求。

旧版保存的计划与历史没有此字段，按当时的 120 秒读取，保留旧记录的准确性；可以在「定时计划」中修改后保存。单次检测的超时设置不覆盖定时计划。兼容性验证仍使用独立的 35 秒上限，不受评测计划影响。

## 题目与评分

| 测试 | 本机检查 | 解释范围 |
| --- | --- | --- |
| 糖果策略 | 返回严格 JSON 整数，参考最小保证预算为 21 | 检查该道最坏情况策略题 |
| 鹈鹕骑自行车 | 展示生成的 HTML/SVG 2D 动画，不做结构评分 | 由用户直接观看实际作品 |
| 判题能力 | 对 6 道原创答案判断题逐项比对布尔标签 | 检查这些算术、逻辑和概率答案的判断能力 |

题面和规则随结果保存。固定题库便于跨时间比较，也存在记忆题目和针对题目优化的局限，不能证明模型身份，更不能作为标准化 IQ 分数。历史比较仅对相同题库版本、渠道模型、显式推理档位和测试项目显示差值。

### 糖果题的来源与规则

参考实际维护该题型的 [MaShouo/CandyTest](https://github.com/MaShouo/CandyTest)。这不是对原题最早作者的认定。原表为圆形苹果 7、桃子 9、西瓜 8；星形苹果 7、桃子 6、西瓜 4。不同表述对能否途中观察口味、自适应调整形状存在歧义，因此 ahaX 明确采用自己的澄清版本：每次能选形状，不能预知口味；取出后可观察口味并决定下一步，目标是苹果和桃子各一颗且形状不同。

答案 21 的上界：9 颗圆形必有苹果或桃子，12 颗星形必同时有苹果和桃子。下界：每种形状按最坏顺序先出西瓜、再出 7 颗苹果、最后桃子。取得一种形状的桃子并配上另一种形状的苹果，至少经过 12 颗西瓜、7 颗苹果、1 颗桃子、1 颗异形苹果，共 21 颗。测试另外用记忆化 minimax 搜索验证答案，不从生成模型答案反推参考值。

### 鹈鹕题的来源与预览

题型背景参考 [Simon Willison 的 pelican-bicycle](https://github.com/simonw/pelican-bicycle)。0.6.0 使用用户指定的完整提示词，不附加静态标签、结构评分或创作格式要求：

> 创建一个 HTML，内容是 SVG 绘制一个鹈鹕骑自行车的 2D 动画，你不需要任何测试，不要有任何限制

HTML、CSS、SVG 动画和脚本保持原样，成功结果标为「已生成」，没有人为结构分。画廊按渠道分组，每组先展示最近 20 个作品，可展开更早记录。只为可见卡片加载预览，离屏释放框架；作品自动播放，详情保留「重新播放」，不再提供暂停按钮。题目与原文独立可查。

生成页面在浏览器原生 sandbox 框架中执行，与 ahaX 窗口和凭据隔离。安装版使用独立只读预览源，主页面在创建前即限定该源的精确随机路径；预览不能联网、导航到其他本机服务或调用原生功能。依赖外部 CDN 的资源不会加载，但原文完整保留。这个运行隔离不改变发送给模型的提示词。

旧版 SVG 记录继续显示并标记来源，不重跑、不改写为新结果。

### 24 小时检测时间线

「定时评测」中的糖果和判题分别显示最近 24 小时，共 48 个半小时时段。每条时间线对应一个渠道、模型与推理档位，通过、未通过、请求失败、取消与未检测使用各自的状态标记；同一格有多次检测时优先显示异常，并可逐条查看实际报告。空白时段不会伪装成正常。单次检测的回答不混入定时时间线。

### 原创判题任务

沿用 ahaX 原创六题，覆盖算术、等距离平均速度、集合推理、任务排列、条件概率和 Python 表达式结果。程序按已知标签评分，不运行 Python 或其他模型生成代码。产品更名不会改写已有题面、题库名称或版本，继续按原题库比较历史结果，不声称是外部标准 benchmark。

## 定时评测

打开「评测 → 定时评测 → 编辑计划」，选择模型、题目、超时与间隔后点击「保存计划」。首次新建计划默认勾选「启用定时」，保存前不会运行；已有计划保留原启用状态。该弹窗不提供单次开始按钮，页面可直接「暂停计划」或「启用计划」。启用定时意味着授权按计划调用所选模型及评审模型；关闭 ahaX 窗口后托盘进程仍会执行计划，完全退出后停止。

新计划默认间隔 30 分钟，界面提供 10 分钟、30 分钟、1 小时、3 小时、6 小时、每天和 7 天间隔，范围为 10 分钟–7 天；已有的其他合法间隔仍可显示。旧计划没有 `intervalMinutes` 时按原 `intervalHours` 执行，既有每日任务不会自动改成每半小时。

定时最多同时执行一轮，手动和定时共享同一运行名额。重启遇到过期计划只执行一轮，不积压补跑多次；中断中的旧请求不重发。计划所依赖的渠道已删除、模型停用或档位不再有效时，显示错误，不替换成其他模型。

## 记录、导出与删除

记录独立存放在应用数据目录 `evaluations/`，单次与定时合计最多保留最近 100 轮，各自的「记录」只显示对应来源。页面只读取紧凑索引，可见作品和打开的报告才加载完整回答。升级时旧报告建立索引，不必每次刷新读取所有 HTML。

在报告中「导出评测报告」可保存 JSON，包含题目、答案、结果和用量，没有 API Key 或原始鉴权头。桌面显示实际保存路径，新文件名为 `ahaX-evaluation-<轮次ID>.json`，浏览器演示下载使用小写 `ahax-evaluation-<轮次ID>.json`。旧导出文件不改名，桌面导出仍保存在 `evaluations/exports/`。

- **删除一轮：** 在「记录」点击对应行的删除按钮，或打开报告点击「删除本轮评测」。
- **批量删除：** 勾选需要的记录或「全选」，点击「删除所选」，确认数量后执行。
- **删除范围：** 每次以完整轮次为单位，包含这一轮全部渠道、模型与题目的回答、作品和摘要。确认前可取消，确认后无法在应用内撤销。
- **运行中记录：** 不能勾选或删除，需要先停止并等待结束。删除其他历史不会取消当前任务或修改定时计划。
- **导出文件：** 已主动导出的 JSON 保留，不随手动删除或历史轮转清理。

批量删除先检查全部 ID，任一记录不存在或仍在运行时整批不改。报告和历史索引通过暂存与原子提交协调；索引未提交就中断会在重新打开时恢复报告，已提交则清理暂存文件。若文件仍被其他程序占用，界面会提示后续清理状态。

浏览器演示只使用内存中的示例回答，没有真实后台调度、模型请求或持久化。页面采用全局浅色、深色或跟随系统的外观，动画本身保留模型生成的配色。

## Ultra 与评测的区别

Ultra 已作为官方 Codex 的原生多代理选项接入。它会在官方客户端中启用任务委派，并转换为实际 API effort。此页直接请求模型 API，因此仅显示确认过的 API 档位，不将 `ultra` 作为请求参数。详见 [原生 Ultra 能力与官方出处](model-capabilities.md#原生-ultra)。
